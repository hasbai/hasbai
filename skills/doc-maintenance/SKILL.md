# Doc Maintenance

文档原则：

- **按需取用**：Agent从入口定位资料，只读任务所需文档。
- **体系规范**：明确职责与范围。同一规则只维护一处，其他位置链接引用。

## 文档树结构

|_ README.md: 人类可读，项目介绍、用途、功能。
|_ AGENTS.md: Agent可读，项目结构、开发规范、全局约束、分流入口等，保持简短
|_ docs
  |_ ARCHITECTURE.md: 整体设计、架构、数据流、关键决策及原因
  |_ DESIGN.md: 共用的视觉、交互和组件规范，以及必要的验收依据
  |_ module1.md: 子模块特定文档
  |_ module2: 较复杂的部分可以按树结构继续构建文档体系
    |_ page1.md: 单独页面特定的规则也可以写成文档

- 共通规则放在最近的共同入口或共通文档，专属细节放在对应范围
- 以上为结构参考，不要硬套

## 维护流程

1. **加载指令并定范围**：先读 doc 插件的 `asd-ste100/SKILL.md` 及其 `references/rules.md`。按已安装的技能入口定位，不写入机器专属路径。再检查工作区和适用的 `AGENTS.md`，通读目标文档及相关规则。新建文档前，读完它将继承或替代的文档及直接相关内容。范围外不扩读，已有内容不重复读。
2. **核对依据**：用代码、配置、测试和用户明确的决策核对文档。追查漂移时再看相关 Git 差异，提交标题只作线索。区分当前实现与目标要求，存在差异时明确标注，保留目标要求。
3. **更新与归位**：修正影响使用或开发判断的过时、缺失内容。记录以后仍需遵守的要求、规范和偏好；删去重复规则、过时清单和代码已清楚表达的细节。共通内容合并引用，模块细节就近放置，只在内容确有需要时拆分。
4. **一致性核验**：检查文档与实现、用户要求及其他相关文档是否一致；检查改动涉及的链接、内容入口和使用命令。查看最终差异，再完成语言审校和程序校验。
5. **语言规范化**：按 STE100 精简中英文，一句一个意思，一个概念一个术语。保留事实、数字、否定、条件、例外、命令、标识符及链接。不调用 `humanizer-zh`。
6. **程序校验**：用 Node.js 20+ 运行已安装 STE100 技能的 `scripts/ste.mjs check <文件> --json`。修正影响理解的告警，再复核技术含义。合理例外说明原因；不能为通过词表改变契约。无运行环境时报告“未执行程序校验”，不得称通过。交付时说明实际修改、核验结果、剩余告警及未解决差异。

## 增量审计

定期维护、重大合并后，或检查“自上次审计以来”的漂移时，读取 [按 commit 增量审计](references/commit-audit.md)。普通维护不加载该流程。

分支、提交、推送和 PR 按当前任务授权及仓库约定执行；此 skill 不自动要求这些动作。
